# AiChat 故事线写作要求 V2

## 一、项目背景

为 AI 聊天 App 的角色故事线社区创作可持续互动的二游架空爱情向内容。用户主要偏好崩坏：星穹铁道、鸣潮、原神等二游角色。

本版在 V1 的基础上，结合 `assets/` 中的优秀示例，统一“帖子展示内容”“角色记忆点”和“静态 JSON 发布格式”的边界。核心目标不是写完一个短篇，而是建立一组能长期驱动角色互动的关系规则。

## 二、核心原则

1. **角色像角色，恋爱不抹平人格。** 甜蜜必须由角色特有的表达方式承载，不能为了甜而让傲慢、冷淡、狡黠、强势或迟钝的角色突然变成标准恋爱模板。
2. **用户是关系中的主体。** 用户以“你”指代，不写死外貌、性别、姓名和无关经历；已给出的用户设定必须让角色有稳定的称呼、立场和互动理由。
3. **小场景切入，大关系收束。** 正文只写一个有画面感的日常片段，但其中应能看见双方的相处模式、权力关系和情感暗流。
4. **允许张力，维持甜蜜倾向。** 可以拌嘴、试探、命令、占上风或暂时误解，但不得把控制、羞辱、伤害当作甜蜜本身；最终应留下关心、信任、靠近或共同约定。
5. **可重复触发，不设固定结局。** 关系状态应能支撑任务、日常、争执、和好、约会等多类后续互动，而不是只适合一次反转。
6. **“建议角色”是适配建议，不是硬绑定。** 未明确要求指定角色时，使用“（建议角色：XX）”；正文中的姓名、身份和世界观允许被其他本地角色承接，但角色性格关键词、关系结构和互动机制要清楚可迁移。

## 三、内容分层

一条完整故事线分为三层：

| 层级 | 是否展示/导入 | 作用 |
| --- | --- | --- |
| 发现页元数据 | 展示，不导入记忆 | 标题、摘要、标签、作者、日期 |
| `introduction` | 帖子正文展示，不导入记忆 | 角色说明、初始情景、可选互动模块 |
| `memories` | 用户确认后导入角色 | 关系事实、人物设定、称呼、互动规则 |

不要把整篇小说复制进 `memories`。剧情只负责“让读者想进入”，记忆点负责“让角色之后仍能演好”。

## 四、帖子正文要求

### 1. 标题

- 简洁、有记忆点，优先体现关系张力、角色表达方式或一个可联想的场景。
- 可采用“角色和她的XX”“核心称呼”“一句角色式短句”等结构。
- 若渠道要求统一前缀，使用：`AiChat角色线：XX和她的XX`。
- 不使用“第一版”“测试”“某角色同人”等过程性标题。

### 2. 摘要

- 一句话说明关系、冲突或吸引点，建议 20—45 字。
- 不复述标题，不提前泄露完整情绪反转，不使用空泛的“一段甜甜的故事”。

### 3. 建议角色标注

正文首行写：

```text
（建议角色：卡芙卡）
```

如需兼容指定角色，可写“（规定角色：XX）”。随后用 2—4 行说明：

- 该设定适配的角色和原作身份；
- 后文是架空爱情向展示；
- 后文不会自动写入记忆，可由用户替换姓名和世界观。

### 4. 初始情景

- 只选一个小切口：任务结束、临时停留、争执后的台阶、一个日常请求等。
- 正文以短段落和对话为主，建议 500—1200 字；节奏紧，信息不堆砌。
- 角色第一句台词或第一个动作就要显出辨识度。
- 用户用“你”，不用“用户”“你扮演”等系统词。
- 用动作、停顿、未说完的话传递情绪，避免旁白直接宣布“她很爱你”。
- 场景结尾应留下可继续选择、追问、执行任务或升温的空间。

## 五、记忆点要求

`memories` 使用字符串数组。每条只写一个明确主题，建议 5—9 条，总长度控制在可稳定导入的范围内。

必须覆盖：

1. **用户设定**：性格、能力或职业、与角色的关系、重要边界。
2. **固定称呼**：角色如何称呼用户；不同语气下的变体要注明使用条件。
3. **角色背景**：原作身份，以及 3—5 个不可丢掉的性格关键词。
4. **相识经历**：具体到场景、冲突和关系转变原因，不写“日久生情”等空句。
5. **互动模式**：日常习惯、小交易、拌嘴方式、关心方式、和好信号。
6. **关系边界**：哪些行为是可信的调情或性格表达，哪些决定必须尊重用户。
7. **可持续机制**：至少一个能够反复触发的互动规则。

记忆点要写成持续事实，不写“刚才她笑了”“今天发生某事”等单次剧情。

## 六、角色表达爱情的方式

爱情表达必须服从原作人格，可参考以下映射：

- **傲慢/天才型**：用命令、嫌弃和纠错包装照顾。
- **狡黠/愉悦犯型**：用试探、交换和诱导表达兴趣。
- **冷淡/寡言型**：用沉默、等待和极短的允诺表达重视。
- **迟钝/纯真型**：用重复出现的习惯和不解其意的依赖表达喜欢。
- **强势/掌控型**：把“替对方决定”改造成“向对方交付选择权”，让稀有的让步成为甜点。

人物可以撒娇、示弱或直接表白，但必须能解释为该角色在恋人面前的变化，不能抹掉其原有边界、能力与说话习惯。

## 七、补充互动模块

需要长期互动时，可从正文末尾提供 2—4 个机制。每个模块包含：

- **模块名**：短，像社区玩法或双方暗号。
- **触发方式**：用户怎样发起。
- **角色反应**：角色会做什么。
- **示例**：一句用户输入和一句角色式回应。

建议模块类型：日常小交易、争执后和好协议、二选一试探、未完成清单、危险任务底线、奖励兑换、角色偶尔破例的信号。

模块不要求角色拥有超能力，也不要制造必须执行的固定结局。

## 八、静态 JSON 格式

详情文件放在 `assets/<storyId>.json`，文件名必须与 `storyId` 一致：

```json
{
  "schemaVersion": 2,
  "storyId": "kafka-and-her-contract-partner",
  "version": 1,
  "title": "卡芙卡和她的合约搭档",
  "author": "AiChat 创作组",
  "publishedAt": "2026-10-12T00:00:00Z",
  "summary": "一句话摘要",
  "tags": ["恋爱", "崩坏：星穹铁道", "星核猎手"],
  "introduction": "帖子正文",
  "memories": ["持续关系设定", "持续互动规则"],
  "images": []
}
```

同时在根目录 `index.json` 增加发现页元数据。索引条目包含：

```json
{
  "storyId": "kafka-and-her-contract-partner",
  "title": "卡芙卡和她的合约搭档",
  "author": "AiChat 创作组",
  "publishedAt": "2026-10-12T00:00:00Z",
  "summary": "一句话摘要",
  "tags": ["恋爱", "崩坏：星穹铁道", "星核猎手"],
  "file": "assets/kafka-and-her-contract-partner.json"
}
```

图片放入 `assets/img/`，详情中的路径写成 `img/<文件名>`；无图片时保留空数组。

## 九、发布前自检

- JSON 严格可解析，UTF-8 编码正确。
- `index.json` 的 `storyId`、标题、摘要、标签与详情一致。
- `file` 路径存在，文件名与 `storyId` 一致。
- 正文只出现一个主要场景，不写成长篇梗概。
- 建议角色的原作身份和核心性格准确，不靠改写原作来迁就恋爱。
- 称呼固定且在记忆点中说明。
- 删除整段剧情后，关系仍能成立并继续互动。
- 记忆点不包含单次动作、原文全文、系统说明或无需长期保存的过场。
- 最后通读一遍：把角色名遮住，是否仍能从说话方式认出她？
